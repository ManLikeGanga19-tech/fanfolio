# M3 Wallet and ledger: plan

**Done when (brief):** every test ends with the ledger balanced; a replayed idempotency key never charges twice; 100% line and branch coverage on the Wallet module (and on the money paths Subscriptions will call).

**Sources:** spec "Wallet and ledger" (postings table, spend flow, top-up flow, payout flow, integrity checks), data model (`ledger_*`, `topups`, `payouts`), "API contracts" (`/wallet`, `/wallet/topups`, `/webhooks/{gateway}`, `/studio/payouts`, Idempotency-Key, problem+json), SEC-04, SEC-12, SEC-13, SEC-14; brief rules 1–4, 11, 12, 14 and the open decisions (top-up processor, payout rails, credit refund policy, tax); decisions D-04 (bonus credits), D-13 (second factor before payouts), D-16 (VPN rules). Screens canvas: FanCore · Wallet & top-up, FanMore · Top-up success, FanProfile · Purchases & receipts, StudioEarnings, AdminPayouts, AdminDisputes, AdminSettings, and the money tiles on AdminOverview.

**No new dependencies or paid services.** Top-ups, payouts and disputes go through the existing gateway interfaces with Fake drivers (`TopUpGateway`, `PayoutGateways`, `FxRateProvider`) plus two new interfaces with Fakes: `DisputeGateway` and `NetworkRiskCheck` (D-16). Never a real processor in tests.

## Money model

- One currency in the ledger: **USD cents**. A credit is one cent (100 credits = $1, `fanfolio.money.credits_per_usd`). Fans see credits, with an approximate amount in USD or KSh beside them (D-21), from `FxRateProvider`, for display only. Nothing is ever stored or computed in another currency.
- Integers only (`App\Support\Money\Money`). The 20% fee is basis points (`platform_fee_bps` = 2000); the creator share is `amount − fee`, with the fee rounded down, so the parts always sum to the whole.
- Fans spend credits and never withdraw them (rule: credits are spent, never withdrawn). Only creator earnings are paid out.

**Append-only (rule 2, SEC-12):** triggers refuse UPDATE, DELETE and TRUNCATE on `ledger_transactions` and `ledger_entries`, like the audit log already does. Mistakes are fixed with a reversing transaction. A test proves the triggers fire. (Revoking UPDATE/DELETE from the app's database role as well belongs in Terraform with the production roles.)

All migrations are new tables only: reversible and safe for zero-downtime deploys.

## The ledger (one entry point)

- `Wallet\Contracts\Ledger::post(LedgerTransaction)`: the **only** code that writes entries or balances (rule 1, spec "Money moves only through Ledger::post"). It refuses a transaction whose debits and credits differ, a zero or negative amount, mixed currencies, or a debit that would take a fan wallet below zero. It writes the transaction, the entries and the cached balances in one DB transaction, and returns the stored result for a repeated idempotency key.
- **Locking (rule 4):** every money-moving call takes a Redis lock on `wallet:{owner}` (2 s TTL, `wallet_lock_ttl_seconds`) and `SELECT … FOR UPDATE` on the balance rows it changes, always in account-id order so two calls cannot deadlock.
- An architecture test fails the build if any class outside `Wallet\Actions\Ledger*` writes to these tables, or if a float appears in Wallet.

**Postings** (the spec's table, plus D-04):

| Event | Debit | Credit |
|---|---|---|
| Top-up confirmed (signed webhook only) | processor_clearing | fan_wallet |
| Top-up bonus (D-04) | platform_promotions | fan_wallet |
| Sale: subscribe, PPV, tip, paid message (called by M5/M6) | fan_wallet (100%) | creator_pending (80%) + platform_revenue (20%) |
| Hold released after 7 days (nightly) | creator_pending | creator_earnings |
| Payout requested | creator_earnings | payout_clearing |
| Payout sent | payout_clearing | processor_clearing |
| Payout failed | payout_clearing | creator_earnings |
| Chargeback | see D-20 below | processor_clearing |
| Refund by an admin | creator_pending + platform_revenue | fan_wallet |

## Actions, contracts and events

- `StartTopUp` (`POST /wallet/topups`, Idempotency-Key): a pack from `fanfolio.topup.packs`, card or crypto (crypto switchable in settings), refused for a frozen wallet or (D-16) a VPN when that rule is on. Returns the gateway's hosted checkout URL. No card data touches our servers.
- `ReceiveGatewayWebhook` (`POST /webhooks/{gateway}`): verify signature and timestamp (older than 5 minutes refused, SEC-13), store the raw payload, answer 200 at once, process on the `payments` queue, deduplicate on the event id. `PaymentSucceeded` posts the top-up (and the bonus); `PaymentFailed` marks it failed; `Chargeback` opens a dispute.
- **`Wallet\Contracts\Purchases::charge(fanId, creatorId, amount, kind, reference, idempotencyKey)`** for M5 and M6: checks `CreatorEligibility::canEarn` (no sale to a suspended or unverified creator, rule 9), the frozen flag and the balance, posts the sale with the fee split, and returns the transaction id so the caller writes its entitlement in the same DB transaction. Insufficient credits is a typed error (`insufficient_credits`). Dispatches `PurchaseCompleted` after commit. M3 builds and fully tests it; M5 is the first caller.
- `ReleaseHeldEarnings` (nightly): moves each sale older than 7 days from pending to earnings, skipping sales tied to an open dispute.
- `RequestPayout` (Studio, `step-up:second-factor` per D-13): amount ≥ minimum ($20) and ≤ available earnings, to the creator's default payout method; refused when `canEarn` is false, payouts are paused (M8a use case 13), the account is restricted, or (D-16) a VPN is detected. Flags: over $1,000 (rule 3, always manual), new payout method in the last 7 days, new device, payout name does not match ID. **Under $1,000 with no flags is approved automatically** (canvas AdminPayouts); otherwise it waits for an admin.
- `ApprovePayout` / `HoldPayout` (admin, audited): approve sends through `PayoutGateways::for(rail)` on the `payments` queue; a failure returns the funds; `PayoutSent` on success. Hold keeps the funds locked and asks the creator for more information.
- `RefundPurchase` (admin, audited, reason required): reverses a sale back to the fan's wallet.
- `AcceptDispute` / `SubmitDisputeEvidence` (admin): through the new `DisputeGateway` (Fake). Evidence is gathered automatically from our logs as on the canvas (3-D Secure result, device and IP history, credits spent after the top-up, statement descriptor).
- `VerifyLedgerIntegrity` (nightly): every transaction balances, every cached balance equals the sum of its entries, and clearing accounts reconcile with the gateway's settlement figures (Fake). Any mismatch is logged as critical (paging comes with M9 observability) and shown on the admin Overview.
- **Events (after commit):** `WalletToppedUp`, `PurchaseCompleted`, `PayoutRequested`, `PayoutSent`, `PayoutFailed`, `ChargebackReceived`. Every change to money writes to Audit (rule 12).

## Tests

- **Every Wallet test ends with the ledger balanced** (a Pest `afterEach` in the Wallet suite asserts the sum of debits equals credits, per transaction and overall, and that cached balances equal their entries).
- Replaying an Idempotency-Key never charges twice (top-up start, webhook replay, purchase, payout request); the same key with a different body is refused.
- Concurrency: many purchases for one fan at once never overspend; two transfers never deadlock.
- Webhooks: bad signature, stale timestamp, replayed event id, out-of-order events.
- Postings for every row of the table above, including the fee rounding at 1-cent amounts.
- Append-only: UPDATE and DELETE on ledger tables fail.
- Payout rules: minimum, available balance, step-up required, flags, auto-approval under $1,000, manual review over $1,000 (rule 3), failure returns funds, a suspended creator cannot withdraw.
- 100% line and branch coverage on `app/Modules/Wallet` (CI gate); axe and keyboard checks on every new screen.

## Owner decisions (24 Nov 2026, logged in docs/decisions.md)

- **D-20 Chargebacks on spent credits:** unspent credits first, then claw back the sales they paid for, newest first; bonus reversed; creator earnings may go negative and are repaid first; the fan's wallet stays frozen until an admin decides.
- **D-21 Display currency:** USD or KSh, chosen in the fan's profile (default KSh for a Kenyan browser), display only. The setting and the "≈" amounts arrive with the Wallet screens (PR 2). Live rate feed: new open item; hidden in production until chosen.
- **D-22:** no payout fees until providers are contracted; receipts and statements are printable pages, no PDF library.
