# M2 Creator KYC: plan

**Done when:** an unverified creator cannot publish or earn; we keep only the provider's reference and result, never ID images.

**Sources:**
- Spec: module boundaries (Creators owns `creators`, `creator_kyc`, `payout_methods`; events `CreatorApproved`, `CreatorSuspended`), data model, payout flow, SEC-04 (step-up for payout-method changes), SEC-10 (encrypted PII), SEC-14.
- Screens: Creator onboarding boards 1–8 (Become a creator, Profile basics, Scan your ID, Selfie liveness, Payout method, Review & submit, In review, Action needed).
- Rules 8, 10, 11, 12, 13. Decisions D-01, D-02.

No new dependencies. KYC goes through the existing `Identity\Contracts\IdentityVerifier` (Fake driver), and payout rails through `Wallet\Contracts\PayoutGateway` (Fake drivers).

## Tables (Creators module)

| Table | Key columns |
|---|---|
| `creators` | ULID, `user_id` unique, `handle` citext unique, `display_name`, `category`, `is_adult`, `kyc_status` (not_started, pending, review, approved, action_needed, rejected), `status` (onboarding, submitted, active, suspended), `submitted_at`, `approved_at`, `terms_accepted_at`, `subscription_price_minor` + `currency` (nullable, set in M5); index(`status`, `category`) |
| `creator_kyc` | ULID, `creator_id`, `provider_ref` unique, `status`, `liveness_passed`, `age_over_18`, `id_type`, `document_last4`, `document_expires_at`, `legal_name` (encrypted), `dob` (encrypted), `failure_reason`, `suspected_fraud`, `checked_at`. One row per attempt. **No image columns** (rule 10). |
| `payout_methods` | ULID, `creator_id`, `rail` (bank, usdt, paxum), `details` (encrypted JSON: bank and account number, wallet address or Paxum email), `display_hint` (for example "Equity ····4821"), `account_name` (encrypted), `name_matches_kyc`, `is_default`, `revoked_at` |

Legal names, dates of birth and payout details are encrypted at the field level (rule 11, SEC-10). Staff screens show only the masked hint (rule 13).

## Actions and contracts

- `StartCreatorApplication`: an existing fan account becomes an applicant. It must have MFA (SEC-04: creators need a passkey or authenticator), so sign-in methods are set up first if missing.
- `SaveProfileBasics`, plus a handle availability check (reserved words, format, case-insensitive uniqueness).
- `StartCreatorKyc` / `CompleteCreatorKyc`: a provider session for `VerificationPurpose::CreatorKyc`. The result is always fetched from the provider, never read from the browser. Only the reference, the result and the date are kept.
  - Under 18 or suspected fraud: rejected, audited, and a `CreatorKycFailed` event for Trust & Safety (case handling arrives in M8).
  - Blurry or unreadable: the "Action needed" screen, with a retake.
- `AddPayoutMethod` / `RemovePayoutMethod`: need a step-up in the last 10 minutes (SEC-04). The rail details are checked (account number, TRC-20 address, email), and the account name is compared with the KYC legal name.
- `SubmitApplication`: needs the profile, a passed KYC and a payout method, plus both statements from the Review & submit board (Creator Terms and the 20% fee; the co-performer statement as worded per D-02).
- `ApproveCreator` / `RejectCreator` / `RequestCreatorFix`: staff only, audited. They set the user's role to creator and dispatch `CreatorApproved`.
- `SuspendCreator`: dispatches `CreatorSuspended`, stops publishing and earning at once.
- **Public contract `Creators\Contracts\CreatorEligibility`:** `canPublish(userId)` and `canEarn(userId)`. True only for an approved creator, with passed KYC, an unexpired ID and an active status. Content (M4) and Wallet/Subscriptions (M3, M5) must call it. This is the M2 "Done when" gate.
- `KycExpiryReminders` (scheduled): reminds 30 days before the ID expires ("We'll remind you 30 days before"). Once the ID has expired, `canPublish` and `canEarn` return false.

Events, all dispatched after commit: `CreatorApplied`, `CreatorKycPassed`, `CreatorKycFailed`, `CreatorApproved`, `CreatorSuspended`. Every change to verification or payout details writes to Audit (rule 12).

## Endpoints and screens (fan PWA, auth-style layout)

| Board | Route |
|---|---|
| 1 Become a creator | `GET /creator/start`, `POST /creator/start` |
| 2 Profile basics (step 1 of 4) | `GET/POST /creator/profile`, `GET /creator/handle-check?handle=` |
| 3–4 ID and selfie (steps 2–3) | `POST /creator/kyc` → the provider's hosted flow; `GET /creator/kyc/return?ref=` |
| 5 Payout method (step 4) | `GET/POST /creator/payout` (step-up) |
| 6 Review & submit | `GET/POST /creator/review` |
| 7 In review / 8 Action needed | `GET /creator/status` |

- **Staff:** a minimal Filament page, "Creators awaiting KYC", with approve, reject and request a fix (all audited). It shows the masked document details; the document image is fetched from the provider on demand and never stored (D-01). The full approvals board comes in M8.
- **Studio:** the `/studio` Filament panel shell. Only approved creators get in; everyone else is sent to `/creator/status`.

## Decisions taken from the docs (to log in docs/decisions.md)

- **D-08 Profile photo:** board 2 has a "Profile photo" upload, but rule 5 says no media is stored as public before malware and abuse-hash scanning, and that pipeline is M4. In M2 the page shows initials; the photo upload arrives with M4 scanning.
- **D-09 Categories:** the spec gives `category` but no list. The screens use Music, Comedy, Fitness, Art and Lifestyle. These become `fanfolio.creators.categories` (config, editable later).
- **D-10 Manual review:** board 7 shows "Manual review: in progress" after the automatic check, while approval boards are M8. M2 ships a minimal staff approve/reject page so the flow can finish; M8 replaces it with the full board.
- **Tax details (KRA PIN):** board 7 shows "Tax details · Needed before payout". Tax rules are an open decision: M2 shows the row as "Needed" and collects nothing.

## Tests (tests first for access and verification)

- The eligibility contract: false for applicants, pending, review, rejected, suspended and expired-ID creators; true only when approved.
- A KYC result is never taken from the browser. A tampered `ref` belonging to someone else is refused.
- No image, selfie or document number column exists. An architecture test scans the Creators migrations for image or blob columns.
- `legal_name`, `dob` and payout details are unreadable in the database (encrypted).
- Under 18 or fraud: rejected, `CreatorKycFailed` dispatched, audited.
- Payout method changes need a step-up. The name-match flag is set correctly.
- Submit refuses an incomplete application. Approve, reject and fix are staff only and audited.
- The Studio panel refuses non-approved creators.
- Handle rules: reserved words, case-insensitive uniqueness, availability check rate-limited.
- Browser checks: axe, keyboard and focus on every new screen.
